## 1. What this is

**statted** is an A-League player & team analytics site built on the
[SkillCorner](https://skillcorner.com) × PySport **open broadcast-tracking data** (in
`../data/`). A working **React + Vite SPA** already exists under `statted/` (staged inside the
`opendata` repo; destined for its own private repo `mgmt-alt/statted`). The goal of the next
phase is a **polished, branded, responsive website** — the analytics/logic are done and
correct; what's open is the visual/product design.

**Live preview of the current build:** https://claude.ai/code/artifact/178d59ab-66f1-405a-9739-82d49dd17b99
(a single-file snapshot; not auto-updating).

## 2. The data (already generated — don't re-derive)

Two JSON files, embedded in the app at `statted/src/data/` (regenerated by the Python
pipeline in `../src/visualization/`):

- **`season_players.json`** — `{ meta, players[] }`. ~268 players, one row each (primary
  position). `meta.metrics` is a **metric registry** (80+ entries: `{key,label,silo,src,better,scoring,fmt}`)
  that drives the explorer/drill-down generically. `meta.run_families`, `meta.positions`, etc.
- **`sample_events.json`** — `{ meta, players{by id} }`. The 10 fully-tracked matches: per-player
  shooting/defending/dribbling counts, calculated metrics, and coarse **heat-map grids**
  (`grid.{touch,defend,run}`, `meta.grid_cols/grid_rows/layers`).

**Two-tier data scope (important):** Pace/Physical/Passing/Creation/Movement come from the
**full-season** aggregates; Shooting/Defending/Dribbling come only from the **10 tracked
matches** (~155 players). There is **no per-shot xG** in the open data (there is an
expected-*shot* value, but only on defensive engagements). No player photos exist either.

To refresh data: rebuild in `../src/visualization/` and copy the two files from
`src/visualization/output/` into `statted/src/data/`.

## 3. The scoring model (settled — keep identical unless asked)

Eight silos → a 0–100 **Statted Score**. Every metric becomes a Weibull percentile; each silo
is a weighted blend; the overall is a weighted mean of silos.

**Two percentile bases, chosen by mode (do not mix them):**
- **By position (role-fit):** every silo percentiled **within position**, combined with
  `POSITION_WEIGHTS`. "How good for your role."
- **Custom weights / archetypes (absolute):** every silo percentiled **league-wide**, so a
  cross-position mix is on one scale.

**Sample composites (in `src/lib/data.js` / `src/visualization/player_score.py`):**
- Shooting = `shots + 3·goals` (volume total).
- Dribbling = `takeons` (volume total).
- Defending = `(2·clearances + 3·danger_prevented + 0.5·regains) / appearances` — a
  **per-appearance rate of last-line actions**. This was hard-won: earlier volume/pressing
  formulas ranked pressing forwards as the best "defenders" and never surfaced centre-backs;
  this version puts ball-winning midfielders, full-backs and centre-backs on top and removes a
  games-played bias. Shooting/Dribbling stay volume totals (sparse events — a rate lets a
  one-game cameo top them).

Constants live in `src/lib/constants.js` (silo weights, `POSITION_WEIGHTS`, `LB_MODES`
archetypes, club colours). Scoring logic in `src/lib/scoring.js`. The JS and the Python
(`player_score.py`) are kept in lock-step.

**Known honest limits:** 10-match sample is small (1–4 apps/player); broadcast tracking is
possession-centric so centre-back positional defending is under-measured; ~97% tracking-ID
accuracy. These are documented in the output README and should stay visible in the UI.

## 4. What's built (SPA architecture)

Vite + React (JS/JSX), `HashRouter`, `base: './'` (works on any static host).

```
statted/
  src/
    main.jsx, App.jsx            # router + nav + theme toggle
    styles.css                   # theme tokens (light/dark) + all component CSS
    lib/
      constants.js               # silos, weights, archetypes, colours
      data.js                    # loads JSON, builds composites + both percentile bases
      scoring.js                 # overall, contributions, team aggregation, metric access, fmt
      store.jsx                  # filters context (positions + min matches)
      tip.js                     # DOM tooltip singleton
      csv.js                     # CSV export
    components/
      Home, Leaderboard, Explorer, Profile, Radar (Compare),
      Athletic, Passing, Shooting, RunMix, Heatmaps   # one graph per file
      Scatter, DataTable, Crest, FilterBar, ViewToggle, ThemeToggle
  src/data/*.json                # embedded datasets
  src/logos/                     # (optional) drop licensed club logos here -> used over crests
```

Shared behaviours: position + min-match **filters** (global context); a per-graph
**Players/Teams** toggle; **club crest badges** (drawn shields in club colours — official
logos are trademarked and intentionally not embedded; a `src/logos/` drop-in swaps in
licensed files); light/dark theme.

Run: `cd statted && npm install && npm run dev` (or `npm run build` / `npm run preview`).

## 5. What "fully designed" should tackle (the brief)

The logic is done; this is a **visual/product design** pass. Open directions (let the user
choose):

- **Brand & identity:** logo/wordmark, colour system beyond the current dev palette,
  typography (currently system fonts — a real typeface would lift it), spacing scale, dark
  mode as a first-class design not just a token swap.
- **Layout & IA:** a proper landing page; whether the 10 views stay top-level or regroup
  (e.g. "Rankings / Explore / Players / Teams"); responsive nav (the current bar wraps — a
  mobile menu is needed); page headers, empty states, loading states.
- **Component polish:** chart styling (axes, gridlines, tooltips), card system, the crest
  badges (or real logos if licensed), player pages as a richer "player profile" destination.
- **Data storytelling:** highlight reels, "player of the round", comparison shareables,
  per-club pages.
- **Tech choices to confirm:** stay vanilla React + CSS, or adopt Tailwind / a component lib /
  TypeScript / a charting lib (currently hand-rolled SVG). Keep it buildable to static for
  GitHub Pages.
- **Deployment:** create `mgmt-alt/statted` (the Claude GitHub app can't create repos — 403 —
  so the user must create it and grant access), then a GitHub Actions → Pages workflow. Note:
  Pages on a private repo needs a paid plan; otherwise make it public to go live.

**Guardrails:** keep the scoring model and data scope intact and their honesty notes visible;
don't embed unlicensed logos/photos; keep the build static-hostable.
